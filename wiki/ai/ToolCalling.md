### 什么是工具调用？

工具调用（Tool Calling）可以理解为让 AI 大模型 **借用外部工具** 来完成它自己做不到的事情。

跟人类一样，如果只凭手脚完成不了工作，那么就可以利用工具箱来完成。

工具可以是任何东西，比如网页搜索、对外部 API 的调用、访问外部数据、或执行特定的代码等。

比如用户提问 "帮我查询上海最新的天气"，AI 本身并没有这些知识，它就可以调用 "查询天气工具"，来完成任务。

### 工具调用的工作原理

其实，工具调用的工作原理非常简单，**并不是 AI 服务器自己调用这些工具、也不是把工具的代码发送给 AI 服务器让它执行**，它只能提出要求，表示 "我需要执行 XX 工具完成任务"。而真正执行工具的是我们自己的应用程序，执行后再把结果告诉 AI，让它继续工作。

虽然看起来是 AI 在调用工具，但实际上整个过程是 **由我们的应用程序控制的**。AI 只负责决定什么时候需要用工具，以及需要传递什么参数，真正执行工具的是我们的程序。

### 工具调用的流程

1. **工具定义**：程序告诉 AI "你可以使用这些工具"，并描述每个工具的功能和所需参数
2. **工具选择**：AI 在对话中判断需要使用某个工具，并准备好相应的参数
3. **返回意图**：AI 返回 "我想用 XX 工具，参数是 XXX" 的信息
4. **工具执行**：我们的程序接收请求，执行相应的工具操作
5. **结果返回**：程序将工具执行的结果发回给 AI
6. **继续对话**：AI 根据工具返回的结果，生成最终回答给用户

### Tools 在 Agent 中的角色

在 [[AIAgent|Agent]] 架构中，Tools 是最小的能力单元，是粒度最小的一层：

- **Tools**：只负责「执行」，本身没有任何决策能力，被动等待被调用
- **Agent**：拿着工具自己做决定，主动判断什么时候调哪个 Tool
- **Workflow**：把 Agent、LLM、Tools 组织成确定性流程

### 工具设计原则

好的工具设计对 Agent 的表现至关重要。核心原则：

**职责单一**：一个工具只做一件事，不要把「查天气 + 发邮件」混在一个工具里。LLM 在判断该不该调用一个工具时，是根据工具描述来的，如果一个工具干的事太杂，模型就很难精确判断什么时候该用它。

**描述要精确**：模型完全靠你写的 description 来理解这个工具能做什么。描述写得含糊，比如只写「查询数据」，模型就可能在不该用的时候去调它；写成「查询公司内部销售数据库，支持按日期和产品类别筛选，返回销售额和订单数」，模型就能精确判断什么场景该用它。

**错误信息要清晰**：工具执行失败时，返回给 LLM 的错误信息必须是它能「看懂」的，比如「参数 city 不能为空」就比「Error code 400」好得多，因为前者能帮助 LLM 自己修正参数重试。

**参数设计要简洁**：能少传的参数就不传，能有默认值的就给默认值，因为 LLM 填的参数越多，出错的概率就越大。

### 工具的定义格式

工具需要给 LLM 配一份「说明书」（schema），让 LLM 知道它存在、以及怎么用：

```python
tools = [
    {
        "name": "web_search",
        "description": "在互联网上搜索信息，适合查询实时数据或不确定的知识",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "搜索关键词，越具体越好"}
            },
            "required": ["query"]
        }
    },
    {
        "name": "send_email",
        "description": "向指定邮箱发送一封邮件",
        "parameters": {
            "type": "object",
            "properties": {
                "to": {"type": "string", "description": "收件人邮箱地址"},
                "subject": {"type": "string", "description": "邮件主题"},
                "body": {"type": "string", "description": "邮件正文内容"}
            },
            "required": ["to", "subject", "body"]
        }
    }
]
```

### 工具调用 vs Function Calling

**Function Calling** 是 OpenAI 提出的术语，指的是模型输出结构化 JSON 来表示要调用的函数和参数。

**Tool Calling** 是更通用的说法，泛指模型调用外部工具的能力。

现代 LLM（GPT-4、Claude 3 之后）基本都原生支持 Function Calling / Tool Use，模型可以直接输出结构化的 JSON 工具调用，不再需要靠解析文本格式。

### Function Calling 的详细原理

#### 三个角色分工

Function Calling 中有三个角色，可以用公司组织来类比：

| 角色 | 类比 | 职责 |
|------|------|------|
| **开发者** | HR（人力资源） | 编写工具的 schema 定义，告诉模型有哪些工具可用 |
| **模型** | 经理 | 做决策——判断什么时候该调用工具、调哪个工具、传什么参数 |
| **代码** | 员工 | 实际执行工具，拿到结果后汇报给模型 |

关键点：**模型只做决策，不执行**。执行永远由开发者写的代码完成。

#### 工具定义 Schema 的字段含义

```json
{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市的当前天气信息",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {
                    "type": "string",
                    "description": "城市名称，如：北京、上海"
                },
                "unit": {
                    "type": "string",
                    "enum": ["celsius", "fahrenheit"],
                    "description": "温度单位，默认摄氏度"
                }
            },
            "required": ["city"]
        }
    }
}
```

各字段说明：

- **name**：工具名称，模型在输出调用时会引用这个名字
- **description**：**最重要的字段**。模型完全依赖 description 来理解工具的功能和使用场景。description 写得好不好，直接决定模型能不能正确判断什么时候该用这个工具
- **parameters**：JSON Schema 格式，定义工具接受的参数
  - **type**：参数类型（string、number、boolean 等）
  - **description**：每个参数的含义说明，帮助模型正确填充参数值
  - **required**：必填参数列表
  - **enum**：可选值限制，缩小模型的选择范围，减少出错

#### 完整的调用流程

Function Calling 的完整流程是 **两轮对话 + 中间执行**：

```
第一轮对话（请求）：
  开发者 -> 模型：system（工具定义）+ user（用户问题）

第一轮对话（响应）：
  模型 -> 开发者：finish_reason = "tool_calls"，返回结构化 JSON 调用请求

中间执行：
  开发者代码解析 JSON -> 执行工具 -> 拿到结果

第二轮对话（请求）：
  开发者 -> 模型：把工具执行结果作为 tool message 发回去

第二轮对话（响应）：
  模型 -> 开发者：finish_reason = "stop"，返回最终回答
```

#### finish_reason 信号机制

模型返回的 `finish_reason` 字段是关键的信号：

- **"stop"**：模型认为对话可以结束了，直接返回文本回答
- **"tool_calls"**：模型判断需要调用工具，返回的是结构化的调用请求而不是文本回答

开发者代码需要检查 `finish_reason`，如果是 `"tool_calls"`，就解析其中的函数名和参数去执行工具，而不是直接把内容展示给用户。

#### 并行工具调用

`tool_calls` 是一个**列表**，模型可以在一次响应中同时返回多个调用请求：

```json
{
    "finish_reason": "tool_calls",
    "tool_calls": [
        {"id": "call_1", "function": {"name": "get_weather", "arguments": "{\"city\": \"北京\"}"}},
        {"id": "call_2", "function": {"name": "get_weather", "arguments": "{\"city\": \"上海\"}"}}
    ]
}
```

并行调用的前提条件：**工具之间没有依赖关系**。比如同时查北京和上海的天气是可以的，但如果第二个工具需要第一个工具的返回结果，就不能并行。

### Function Calling 的训练原理

#### 预训练学不会 Function Calling

预训练阶段模型学不会 Function Calling，原因是：**预训练语料里没有标准的工具调用 JSON 模式**。预训练语料主要是自然语言文本（网页、书籍、代码等），而 Function Calling 要求模型输出高度结构化的 JSON 格式（函数名 + 参数），这种格式在预训练数据中几乎不存在。

#### SFT 阶段：教会怎么调

监督微调（SFT）阶段的核心目标是教会模型 **怎么调**——即输出正确的 JSON 格式。

训练样本是一个**完整的对话**：

```
1. system message：包含工具定义（schema）
2. user message：用户的问题
3. assistant message：模型输出的工具调用 JSON（这是要学的目标）
4. tool message：工具执行的结果（模拟返回）
5. assistant message：模型根据工具结果的最终回答
```

模型通过大量这样的完整对话样本，学会了：
- 什么时候输出 JSON 调用格式
- JSON 的正确结构（函数名、参数键值对）
- 如何根据工具返回的结果组织最终回答

#### RLHF 阶段：教会什么时候调

强化学习（RLHF）阶段的核心目标是教会模型 **什么时候调**——建立"该不该调"的边界感。

具体来说：
- 用户问"1+1等于几"→ 不应该调用计算器工具，直接回答
- 用户问"帮我查一下今天的新闻"→ 应该调用搜索工具
- 用户问"帮我订一张明天去北京的机票"→ 应该调用订票工具

RLHF 通过人类反馈的奖励信号，让模型学会判断"这个问题该不该用工具"。

#### 训练数据需要覆盖的场景

| 场景 | 说明 |
|------|------|
| 单工具调用 | 最基本的场景，一个问题调一个工具 |
| 多工具并行 | 一个问题需要同时调用多个无依赖关系的工具 |
| 调用失败重试 | 工具返回错误时，模型能修正参数重新调用 |
| 不需要工具直接回答 | 模型能判断某些问题不需要工具，直接回答 |
| 多轮对话中的工具调用 | 对话上下文中涉及多次工具调用 |

#### 训练数据来源

**人工标注**：
- 质量高，标注者能精确控制样本质量
- 成本高，速度慢，难以大规模覆盖

**模型自动生成 / Self-Instruct / Distillation**：
- 成本低，量大，能快速生成大量训练样本
- 需要注意幻觉传递问题——如果生成模型本身就有错误理解，错误会被传递到训练数据中

**RLAIF（AI 反馈强化学习）**：
- 用 AI 代替人工打分，成本更低
- 风险是 AI 的偏见会被传递到模型中

#### 一句话总结

> **SFT 教会模型怎么调（格式），RLHF 教会模型什么时候调（判断）。**

### MCP（Model Context Protocol）

随着工具越来越多，怎么管理和发现工具本身也变成了一个工程问题。

Anthropic 在 2024 年底提出了 **MCP（Model Context Protocol）**，思路是把工具的注册、描述、调用做成一套标准化协议，这样不同的 Agent 框架和不同的工具提供方就能互通了，不用每接一个新工具就写一套适配代码。

可以把 MCP 理解成工具世界的「USB 接口」，只要工具按这个标准暴露自己的能力，任何支持 MCP 的 Agent 都能直接调用。

### Function Calling vs MCP 详细对比

#### 本质区别

- **Function Calling 是"调用语言"**：定义模型怎么表达调用请求（JSON 格式、参数结构等）
- **MCP 是"工具生态协议"**：定义工具怎么标准化打包、注册和被 AI 客户端发现

#### 关系

MCP 底层靠 Function Calling 驱动——模型最终还是通过 Function Calling 的 JSON 格式来触发工具调用。**模型感知不到 MCP 的存在**，它只知道"我有这些工具可以用"，至于这些工具是怎么注册上来的、从哪个 MCP Server 来的，模型并不关心。

#### 类比

| 概念 | 类比 |
|------|------|
| Function Calling | HTTP 请求格式（定义数据怎么传输） |
| MCP | REST API 设计规范 + 服务注册发现机制（定义服务怎么标准化暴露和被发现） |

#### Function Calling 的痛点

每次都是一次性的——你在代码里写死工具定义，工具多了之后管理困难：
- 工具定义散落在各个项目的代码里
- 换一个 Agent 框架就要重新适配
- 工具提供者和工具使用者之间没有标准化的对接方式

#### 什么时候选 Function Calling

- 快速原型验证
- 工具只为单一应用服务
- 需要精细控制执行逻辑
- 部署环境受限（不需要额外的 MCP Server）

#### 什么时候选 MCP

- 工具需要跨项目复用
- 社区有现成的 MCP Server 可用
- 工具规模大，需要系统化管理
- 在做 [[AIAgent|Agent]] 系统

### Function Calling、Skill、MCP 三层架构

这三者构成了从底层到上层的完整工具调用体系：

```
┌─────────────────────────────────────────┐
│  Agent Skill（最上层）                    │  知识和流程封装
│  拿到工具后按什么流程完成任务               │
├─────────────────────────────────────────┤
│  MCP（中间层）                            │  工具标准化
│  工具怎么暴露给模型、注册和发现             │
├─────────────────────────────────────────┤
│  Function Calling（最底层）               │  调用协议
│  模型怎么触发函数调用                      │
└─────────────────────────────────────────┘
```

- **Function Calling** 是最底层的调用协议——模型怎么调函数（JSON 格式、参数传递）
- **MCP** 在 Function Calling 之上做工具标准化——工具怎么暴露给模型（注册、发现、描述）
- **Agent Skill** 在最上层做知识和流程封装——拿到工具后按什么流程完成任务

#### 完整链条

> **Skill（定义流程）-> MCP（提供工具）-> Function Calling（模型触发调用）**

#### 类比

| 概念 | 类比 |
|------|------|
| Function Calling | "手"——执行具体动作的器官 |
| MCP | "厨房/工具箱"——标准化存放和管理工具的地方 |
| Skill | "菜谱/操作手册"——指导你用工具完成完整任务的流程 |

### 工具调用在 ReAct 中的角色

在 [[ReAct]] 范式中，工具调用是 Action 阶段的核心：

```
Thought: 用户想查天气，我需要调用天气查询工具
Action: get_weather
Action Input: {"city": "上海"}
Observation: 上海今天晴，25°C，微风
```

LLM 输出 Thought + Action，应用程序执行工具后把结果作为 Observation 填回，LLM 再进入下一轮 Thought。

### 常见的工具类型

**信息检索类**：网页搜索、数据库查询、[[RAG|向量检索]]

**计算处理类**：数学计算、代码执行、数据分析

**外部服务类**：发送邮件、创建日历事件、调用第三方 API

**文件操作类**：读写文件、解析文档、生成报告

### 推理模型不支持 MCP 的原因

推理模型（如 o1、DeepSeek-R1 等具有长思考链的模型）在工具调用方面存在特殊的挑战。

#### 根本矛盾

**推理模型的思考链是一次性连续生成的，不能中途打断；而工具调用天然需要在生成过程中暂停等待外部执行。** 这两种生成范式存在根本冲突。

#### 具体问题

1. **生成范式冲突**：推理模型需要一口气完成整个思考过程（CoT），中途插入工具调用会打断推理的连贯性
2. **KV Cache 保存状态代价大**：如果要暂停思考去执行工具，需要保存当前的 KV Cache 状态，这会带来显著的显存占用和吞吐量下降
3. **训练目标冲突**：推理模型的训练目标是"持续深入推理"，而工具调用要求模型"在合适的时机打断自己，输出结构化 JSON"，这两个目标在训练时很难兼顾

#### 解决方案

**让工具调用发生在思考阶段结束之后**：

- **o3**：思考完成后才决定是否调用工具
- **Claude Extended Thinking**：先完成深度思考，再基于思考结果决定工具调用

**Claude 的 interleaved thinking 模式**：允许在多次工具调用之间穿插思考——思考一段 -> 调用工具 -> 拿到结果 -> 再思考一段 -> 再调用工具。这种方式在保持推理深度的同时支持了多轮工具交互。
