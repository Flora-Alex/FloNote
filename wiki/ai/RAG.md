### 什么是 RAG？

RAG（Retrieval-Augmented Generation，检索增强生成）是一种结合信息检索技术和 AI 内容生成的混合架构，可以解决大模型的知识时效性限制和幻觉问题。

简单来说，RAG 就像给 AI 配了一个"小抄本"，让 AI 回答问题前先查一查特定的知识库来获取知识，确保回答是基于真实资料而不是凭空想象。

RAG 的核心思想是：既然模型记不住，那就给它开卷考试。不把知识塞进模型参数里，而是在用户提问的时候，实时去外部知识库检索，把找到的相关内容直接放进 prompt 给 LLM 读。

从技术角度看，RAG 在大语言模型生成回答之前，会先从外部知识库中检索相关信息，然后将这些检索到的内容作为额外上下文提供给模型，引导其生成更准确、更相关的回答。

通过 RAG 技术改造后，AI 就能：

- 准确回答关于特定内容的问题
- 在合适的时机推荐相关课程和服务
- 用特定的语气和用户交流
- 提供更新、更准确的建议

可以简单了解下 RAG 和传统 AI 模型的区别：

| 特性 | 传统大语言模型 | RAG 增强模型 |
| --- | --- | --- |
| 知识时效性 | 受训练数据截止日期限制 | 可接入最新知识库 |
| 领域专业性 | 泛化知识，专业深度有限 | 可接入专业领域知识 |
| 响应准确性 | 可能产生 "幻觉" | 基于检索的事实依据 |
| 可控性 | 依赖原始训练 | 可通过知识库定制输出 |
| 资源消耗 | 较高（需要大模型参数） | 模型可更小，结合外部知识 |

### RAG 解决了什么问题？

RAG 主要解决大模型的三个核心问题，这三个问题的根源都是知识被固化在了模型参数里。

**第一个问题是知识时效性。** LLM 训练完知识就固定了，训练截止日期之后发生的事它一无所知。你问 LLM「今年发布的某款产品有哪些新功能」，如果它的训练数据截止在发布日期之前，它不知道，但它不会说「我不知道」，而是用自己见过的历史规律「推测」出一个听起来合理但实际错误的答案。

**第二个问题是私有知识覆盖。** 公开互联网上的知识 LLM 或多或少见过，但每家公司的内部文档，比如产品手册、客服知识库、合同模板、行业规范，这些东西根本不会出现在公开训练数据里。你让 LLM 扮演客服机器人回答「我们产品的退款政策是什么」，它不可能知道你们公司特定的规定。

**第三个问题是幻觉问题。** 幻觉是知识缺失的副产品。当模型参数里的知识不够用的时候，它只能硬着头皮往下生成，把相关的、不相关的知识拼凑出一个「听起来合理」的答案。幻觉是整个 LLM 应用领域最核心的可信度问题，尤其在医疗、法律、金融这些容错率低的场景里，一个编出来的答案可能直接造成实际损失。

RAG 的解法是把知识存到外部知识库，用的时候实时检索注入，彻底绕开了参数里的知识限制。知识过期的问题——新内容随时入库，不需要重新训练模型；知识缺失的问题——公司文档入库之后 LLM 就能「看到」这些内容；幻觉问题——LLM 有了真实的参考依据，生成答案时是在「复述」检索到的内容，幻觉率显著降低。

### RAG vs 微调（Fine-tuning）

微调和 RAG 是两种不同的知识注入方案，不是谁替代谁的关系：

| 维度 | 微调（Fine-tuning） | RAG |
| --- | --- | --- |
| 知识更新 | 需要重新训练，成本高 | 更新知识库即可，实时生效 |
| 推理延迟 | 低，无额外检索步骤 | 较高，多一次检索耗时 |
| 实现成本 | 高，需要 GPU 和标注数据 | 低，向量库 + Embedding 即可 |
| 答案可溯源 | 不支持，来自模型参数 | 支持，可追溯到具体 chunk |
| 适合场景 | 定制输出风格、深度专业能力 | 私有知识问答、动态更新数据 |
| 知识上限 | 受限于训练数据质量和规模 | 受限于检索质量和 context 长度 |

实际上这两个方案也可以组合使用：先对基础模型做一轮微调，让它学会输出格式、语气风格、行业术语；再用 RAG 来提供具体的知识内容。微调解决「怎么说」，RAG 解决「说什么」，各司其职。

### RAG 工作流程

一个完整的 RAG 系统分**离线**和**在线**两个阶段：

#### 离线阶段：提前把知识准备好

离线阶段的目标很明确：在用户提问之前，就把知识库建好。这一阶段只做一次，建好了后面反复用。

**第一步是文档加载**。把各种格式的原始数据读取进来，可以是 PDF、Word、Markdown、网页、数据库记录等。这一步通常用 LlamaIndex 或 LangChain 提供的 DocumentLoader 来做。

**接下来是文档切割（Chunking）**。不能把整篇文档直接存进去检索，非要切成一块一块的原因有两个：一是向量模型有输入长度限制；二是如果把一整篇文章压缩成一个向量，细节信息会被「平均掉」。

所以要把文档切成小片段（chunk），每个 chunk 代表一段聚焦的内容。实践中通常 500～1000 token 一个 chunk，同时做一定的重叠（比如前后各重叠 100 token），避免把一段完整的语义从中间切断。

**然后是 Embedding（向量化）**。Embedding 模型会把一段文字转成一个高维数字向量，比如一个 1536 维的浮点数列表。语义相似的文本，它们在这个坐标系里的位置就靠近；语义不相关的，位置就离得远。

**最后一步是入库**，把每个 chunk 的向量和原始文本一起存进向量数据库。向量数据库专门优化了高维向量的存储和相似度搜索，常见的有 [[Chroma]]、[[Milvus]]、[[Qdrant]]、[[Weaviate]] 等。

#### 在线阶段：用户提问时实时检索

在线阶段是每次用户提问时实时执行的，对响应速度有要求。

**第一步是 Query 处理**。用户的提问往往是口语化的，或者比较模糊，直接拿去检索效果不一定好。实际工程里会加一步 Query 改写，让 LLM 把用户的问题改写成更适合检索的形式。

**然后是向量检索（粗排）**。把用户的问题也转成向量，然后去向量库里做相似度搜索，找出向量距离最近的 Top-K 个 chunk。这一步速度非常快，即使是百万量级的向量库，通常也能在几十毫秒内返回结果。

**接下来是 Rerank（精排）**。这一步就是为了弥补粗排的不足。Rerank 模型（通常是 Cross-Encoder 结构）会把用户问题和每个候选 chunk 拼在一起，深度理解它们之间的相关性，然后重新排序，把不相关的结果过滤掉。

**最后是生成**，把用户问题 + 精排后的 chunk 拼成 prompt，交给 LLM 生成最终答案。Prompt 里通常会明确告诉 LLM「只根据提供的资料回答，资料里没有就说不知道」，这样能有效抑制 LLM 瞎编的倾向。

### 文档切割（Chunking）策略

文档不能直接存进向量库，必须先切成小块（chunk），每个 chunk 分别向量化之后存成一条记录。

每条 chunk 记录包含三个核心部分：向量用于相似度检索，原始文本是检索命中之后塞给 LLM 读的内容，metadata 是来源文件、页码这些附加信息。向量负责「找到」，原文负责「阅读」，两者缺一不可。

#### 切割策略

**策略一：固定大小切割（Fixed Size Chunking）**

最简单的方式，按固定字符数或 token 数切割，不管语义边界在哪。优点是实现简单、chunk 大小可控；缺点是可能在句子中间截断，破坏语义完整性。

纯固定大小几乎不单独使用，通常会加上**重叠（overlap）**来缓解边界截断问题。重叠量通常设为 chunk_size 的 10%～20%。

**策略二：语义边界切割（Semantic/Structure Based Chunking）**

按文档的自然语义边界来切，比如段落、句子、标题层级。核心思想是：不要在语义中间截断，找到文字天然的「断点」再切。

对于有明确标题结构的 Markdown 或 HTML 文档，按标题层级切是更优的选择：每个 chunk 对应整篇文档中的一个完整章节。

**策略三：特殊内容专项处理**

代码应该以函数或类为单位切割，用语法解析工具（如 Python 的 AST 模块）识别函数和类的边界。表格则要整块保留，转成 Markdown 格式存储，不能按行截断。

**策略四：父子切割（Parent-Child Chunking）**

核心思路是「检索时用放大镜（小块，精准定位），返回时用全景图（大块，上下文完整）」。

存储时，同一段内容存两份。一份是细粒度的小 chunk（比如 200 token），专门用于向量检索；另一份是包含这个小 chunk 前后上下文的大 chunk（比如 1000 token），通过 ID 与对应的小 chunk 关联。

**策略五：Late Chunking**

Jina AI 2024 年提出的思路：先把整篇文档丢给一个支持长上下文的 Embedding 模型，让模型做一次完整的前向传播，输出文档里每个 token 的向量；然后按照 chunk 的边界，把落在同一个 chunk 里的所有 token 向量做 mean pooling。

这样每个 chunk 的向量里已经天然融入了全文的语境。

### Embedding 和 Embedding 模型

Embedding 嵌入是将高维离散数据（如文字、图片）转换为低维连续向量的过程。这些向量能在数学空间中表示原始数据的语义特征，使计算机能够理解数据间的相似性。

Embedding 的关键特性是：语义相近的文本，向量的余弦相似度高。这就是为什么「苹果手机怎么截图」和「iPhone 如何截屏」这两句话用词完全不一样，但 Embedding 之后的向量余弦相似度可能高达 0.95。

#### 常见 Embedding 模型

| 模型 | 维度 | 中文效果 | 是否开源 | 适用场景 |
| --- | --- | --- | --- | --- |
| text-embedding-3-small | 1536（可降维） | 一般 | 否（API） | 英文为主、快速上手 |
| text-embedding-3-large | 3072（可降维） | 一般 | 否（API） | 英文为主、精度要求高 |
| bge-large-zh-v1.5 | 1024 | 很好 | 是 | 中文知识库经典选择 |
| bge-m3 | 1024 | 好 | 是 | 中英混合、多语言、多模式检索 |
| Qwen3-Embedding | 多种可选 | 很好 | 是 | 中文场景新一代强力选择 |

选模型时主要看：中英文比例、数据合规要求、向量维度对存储和检索速度的影响。

#### 如何评估 Embedding 模型？

不要只看 MTEB 这类通用排行榜，一定要在自己的业务数据上跑召回测试。准备几百条业务相关的「问题 + 正确答案 chunk」对，分别用候选模型做检索，看正确的 chunk 有没有出现在前 K 条结果里。

这个指标叫 **Hit@K**，Hit@5 = 0.8 的意思就是，80% 的问题，它对应的答案都出现在了检索结果的前 5 条里。通常 Hit@5 低于 0.7 就要考虑换模型或者改进 Chunking 策略。

### 向量数据库

向量数据库是专门用来存储和检索高维向量的数据库，核心能力是近似最近邻搜索（ANN，Approximate Nearest Neighbor），能在百万甚至亿级的向量里快速找出最相似的几条。

普通关系型数据库的索引结构（如 B-tree）对高维向量基本上是失效的，所以需要专门的数据库来处理这个场景。

#### 核心索引算法

**HNSW（Hierarchical Navigable Small World）**：目前召回率最高的 ANN 算法之一。它构建的是一个多层图结构，查询时从最上层的稀疏图开始导航，逐层收窄范围。优点是召回率高（95%+）、查询速度快；缺点是建索引时内存消耗大。

**IVF（Inverted File Index）**：先对向量做聚类，把相似的向量分进同一个「桶」里，查询时只搜最相关的几个桶。优点是内存占用小、适合超大规模；缺点是精度比 HNSW 略低。

#### 向量数据库选型

| 数据库 | 部署方式 | 适合规模 | 混合检索 | 主要优势 | 主要劣势 |
| --- | --- | --- | --- | --- | --- |
| Chroma | 本地/Client-Server/云 | 中小规模 | 是 | 零配置上手极快 | 超大规模稳定性待验证 |
| Qdrant | 自托管/云 | 中大规模（亿级） | 是 | 性能好，API 简洁 | 超大规模需调优 |
| Milvus | 自托管（分布式） | 大规模（亿级） | 是 | 可水平扩展 | 部署运维复杂 |
| Pinecone | 全托管云服务 | 中大规模 | 是 | 无需运维 | 费用高，数据出境 |
| pgvector | PostgreSQL 插件 | 中小规模 | 是 | 无需新组件 | 性能弱于专用向量库 |

快速原型验证用 Chroma，中小到大规模生产环境推荐 Qdrant，超大规模选 Milvus，不想运维就上 Pinecone，已有 PostgreSQL 的项目直接用 pgvector 插件。

### 向量检索 vs 关键词检索

向量检索和关键词检索（BM25）各有盲区，谁也不能替代谁：

| 维度 | 关键词检索（BM25） | 向量检索 |
| --- | --- | --- |
| 匹配方式 | 词汇重叠统计 | 语义空间距离 |
| 索引结构 | 倒排索引（稀疏） | 向量库（稠密） |
| 同义词处理 | 无法处理 | 天然支持 |
| 精确词命中 | 极好 | 容易漏 |
| 适合场景 | 专有名词、代码、精确查询 | 语义问答、模糊表达 |

向量检索擅长语义相似，能跨越同义词、近义词、不同表达方式的障碍；但它的劣势是对精确词汇不敏感，产品型号「Pro Max 256GB」、人名、版本号这类词，在 Embedding 空间里可能彼此距离并不近。

关键词检索（BM25）对同义词和不同表达方式无能为力，但对精确词语命中率极高。

### 多路召回

既然两种方式各有盲区，而且刚好互补，那最自然的想法就是两路都跑。工程实践中的标准做法叫**混合检索（Hybrid Search）**：同时跑向量检索和 BM25，各自召回一批候选，然后用 RRF（Reciprocal Rank Fusion，互倒排名融合）算法把两路结果合并排序。

RRF 的思路：它不看各路的原始分数，只看排名。排名第 1 的 chunk 贡献的分数最高，排名越靠后贡献越低。把同一个 chunk 在所有路径里的得分加起来，就是它的综合分。

公式是 `score(chunk) = 求和(1 / (k + rank))`，其中 k 是平滑参数，通常取 60。

三路召回的典型组合：
- **向量检索**：负责语义层面的覆盖，处理同义词、近义词
- **BM25 关键词检索**：负责精确词匹配，处理产品型号、专有名词
- **多 Query 扩展**：把用户问题改写成多个不同角度的版本，覆盖更多表述差异

### Query 改写（Query Rewrite）

用户和文档写作者之间有一道天然的表述鸿沟。用户可能这样问：「这东西坏了咋整」，而文档里写的是「产品故障排查与维修指南」。Query Rewrite 就是在检索之前，先对用户的问题做加工，让它在向量空间里离正确文档更近。

#### 改写方法

**直接改写**：把口语化、模糊的问题改写成更精准、更书面化的检索表述。

**HyDE（Hypothetical Document Embeddings）**：先让 LLM 根据用户问题生成一段「假设性的答案」，再用这段假设答案的向量去检索文档。假设答案和文档都是陈述性文字，风格更接近，向量距离也更近。

**Step-back Prompting**：把具体问题「后退一步」，提升到更抽象的层次，先检索背景知识，再结合背景知识回答具体问题。

**多 Query 扩展**：用 LLM 把用户原始问题改写成 3～5 个不同角度的版本，分别去检索，然后把所有结果合并去重。

### Rerank 精排

多路召回之后，候选 chunk 可能有 20~30 个，这些 chunk 里难免混入一些不太相关的内容。Rerank 的作用是从这些候选里挑出最相关的 3~5 个。

向量检索用的是 Bi-encoder 结构：query 和 chunk 各自独立编码成向量，再算余弦相似度。优点是速度极快；缺点是 query 和 chunk 是分开编码的，模型没办法看到两段文字之间的具体词语关联。

Rerank 用的是 Cross-encoder 结构，把「query + chunk」拼成一对输入，让模型整体看这一对的相关性。Cross-encoder 能看到 query 中每个词对 chunk 的影响，相关性判断精度远高于 Bi-encoder。

常用的开源 Rerank 模型有 BGE-Reranker-v2、BCE-Reranker。

### RAG 检索优化策略

RAG 检索优化可以从四个层次来理解：

**索引层**：决定知识怎么「存」。核心思路是 Small-to-Big（小块检索、大块使用），具体实现包括 Parent-Child Chunking、摘要索引、多粒度分层索引。

**查询层**：决定问题怎么「转」。包括 Query 改写、多 Query 扩展、HyDE、Step-back Prompting。

**召回层**：决定知识从哪里「找」。多路召回（向量 + BM25），用 RRF 融合结果。

**重排序层**：决定候选里谁「最相关」。用 Cross-Encoder Rerank 模型做精排。

一个典型的生产级搭配：**Parent-Child 索引 + 向量 BM25 多路召回 + Rerank 精排**。

### 高级 RAG 范式

#### Self-RAG

让 LLM 自己来决定要不要检索，以及评估检索质量。Self-RAG 训练了一个特殊的 LLM，它会自主决定：
- 当前问题需不需要检索？
- 检索回来的内容和问题相不相关？
- 生成的答案有没有幻觉？
- 最终答案质量够不够好？

#### CRAG（Corrective RAG）

检索质量差的时候自动纠错降级。CRAG 在检索完之后加了一个质量评估环节：如果检索到的内容质量高，正常走 RAG 流程；如果质量低，自动切换到网络搜索，用搜索结果代替知识库内容来回答问题。

#### GraphRAG

微软推出的方案，用知识图谱的社区发现和层次摘要来增强全局理解能力。预处理阶段，先用 LLM 从文档里抽取实体和关系，建成知识图谱，然后用社区发现算法对图谱中的实体做聚类，再对每个社区生成一份 LLM 摘要。适合需要全局理解的场景，比如「这批文档的核心主题是什么」。

#### Agentic RAG

把 RAG 做成 Agent，支持多轮的动态检索。LLM 可以自主决定：要不要再检索一次、用什么关键词检索、检索结果是否足够、什么时候可以生成最终答案。适合需要多步骤推理的复杂问题。

### 如何规避 RAG 幻觉

RAG 里的幻觉有两个完全不同的来源：

**检索层没找到**：LLM 没有可用的上下文，靠自身知识在编造答案。

**生成层超发挥**：检索内容召回了但 LLM 没有严格遵循，在文档内容的基础上加了自己的推断。

#### 规避策略

**Prompt 强约束**：明确告知 LLM 只能根据提供的资料回答，资料里没有的就说不知道，不准推断和补充。

**检索质量门控**：Rerank 分数低于阈值就直接拒答，不让 LLM 在低质量上下文上硬撑。

**生成后引用核查**：每个关键的声明都要在 chunk 里找到来源依据。

**结构化输出强制溯源**：让 LLM 输出 JSON，每条结论必须附上来源编号。

### RAG 效果评估

#### 检索层评估

**Hit@K**：正确答案有没有出现在检索结果的前 K 条里。Hit@5 = 0.8 表示 80% 的问题，答案都出现在了前 5 条里。一般 Hit@5 低于 0.7 就说明检索层有问题。

**MRR（Mean Reciprocal Rank）**：平均倒数排名。对每个问题算 `1 / 排名`，然后求平均。第一名找到得 1 分，第二名得 0.5 分。MRR 低于 0.5 通常说明 Rerank 效果不够好。

#### 生成层评估（RAGAs 框架）

**Faithfulness（忠实度）**：答案里说的每件事，在检索到的 chunk 里有没有出处？衡量的是幻觉程度。

**Answer Relevancy（答案相关性）**：答案有没有回答用户问的那个问题？

**Context Recall（上下文召回率）**：要回答这个问题，所需要的信息有多少比例在检索结果里覆盖到了？

**Context Precision（上下文精确率）**：检索结果里「有用的内容」排名是否靠前。

#### 线上指标

- 踩率（thumbs_down_rate）：用户主动点踩的比例
- 追问率（followup_rate）：用户紧接着追问的比例
- 转人工率（escalation_rate）：系统放弃回答转人工的比例
- 空回答率（answer_empty_rate）：系统主动说「我不知道」的比例

### RAG 知识库动态更新

RAG 知识库的更新逻辑是**先删后增**：检测到文档变化后，先把旧文档对应的所有 chunk 删掉，再重新切割入库。

#### 变更检测

给每个文档算一个内容 hash（MD5 或 SHA256），通过轮询或者监听数据源变更，检测到文档新增、修改、删除的时候触发更新。

#### 变更感知方式

**定时轮询（Polling）**：按固定时间间隔扫描所有文档，对比 hash 值。适合文档更新频率低、对实时性要求不高的场景。

**事件驱动（Event-Driven）**：数据源有变更时主动发出消息（通过 Kafka、RabbitMQ、Webhook）。适合实时性要求高的场景。

#### chunk ID 设计

让 chunk ID 带上文档 ID 作为前缀（如 `product_manual_v3_chunk_001`），或者在每个 chunk 的 metadata 里存上文档 ID 字段，方便批量查找和删除。

### RAG 落地难点

**第一难：文档预处理**。PDF 解析容易把表格、双栏内容顺序搞乱；扫描版文档需要 OCR；代码文档切割不当会破坏逻辑完整性。

**第二难：检索质量调优**。Chunking 策略、Query 和文档的语义鸿沟、向量检索对精确词语效果差，这些问题交织在一起，排查起来特别费劲。

**第三难：效果评估困难**。单条答案的对错人工判断成本高，而且不同人的标准不一样。需要建立分层的量化指标体系。
