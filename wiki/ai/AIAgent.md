### 什么是 Agent？

Agent（智能体）是一个以大语言模型（LLM）为核心「大脑」的自主决策系统，能够根据用户给定的目标，自主判断需要调用哪些工具、如何组合这些工具，并在执行过程中动态调整策略，直到任务完成。

Agent 与普通的 LLM 调用最本质的区别在于：普通 LLM 是「一次性」的，你问它一个问题，它直接给出一个答案，中间没有和外部世界的交互；而 Agent 是「循环式」的，它会根据当前情况决定是否需要调用工具、调用什么工具，拿到工具返回的结果后继续思考，形成一个「思考 -> 行动 -> 观察」的循环，直到判断任务完成。

### Agent 与大模型的本质区别

| 维度 | 普通 LLM | Agent |
| --- | --- | --- |
| 交互方式 | 一次性问答 | 多轮循环决策 |
| 工具调用 | 不能直接调用 | 可自主调用外部工具 |
| 信息获取 | 依赖训练数据 | 可实时获取外部信息 |
| 任务处理 | 直接生成答案 | 可拆解多步骤任务 |
| 状态维护 | 无状态 | 维护对话历史和任务状态 |

### Agent 核心架构

一个完整的 Agent 系统由四个核心组件构成：

**规划（Planning）**：负责把复杂任务拆解成可执行的子任务，决定「要做什么」。规划模块让 Agent 具备处理复杂任务的能力，而不是只能回答简单问题。

**记忆（Memory）**：负责存储和检索信息，让 Agent 能够「记住」之前的对话和任务状态。记忆分短期记忆（当前对话历史）和长期记忆（向量数据库存储的历史信息）。

**工具（Tools）**：Agent 可调用的外部能力，比如搜索、计算、执行代码、访问数据库等。工具是 Agent 扩展能力的手段，让它不局限于模型内部的知识。工具的接入和管理可以通过 [[MCP]] 协议标准化，工具的使用流程可以通过 [[AgentSkill]] 封装复用。

**行动（Action）**：负责执行具体的操作，比如调用工具、生成回复等。行动是 Agent 与外部世界交互的接口。

### Tools、Agent、Workflow 的区别

这三者是粒度从小到大的三层结构，最核心的区分角度是「谁来做下一步该干什么这个决策」。

**Tools（工具）**：最小的能力单元，就是封装好的可调用函数，比如搜索、执行代码、发邮件。它只负责「执行」，本身没有任何决策能力。

**Agent（智能体）**：是一个完整的决策系统，内部用 LLM 做大脑，自己判断什么时候调哪个 Tool、要不要继续、什么时候结束，是主动的。

**Workflow（工作流）**：更上层的编排框架，把 Agent、LLM、Tools 组织成一条确定性流程，每个节点做什么、按什么顺序流转都是开发者事先写死的。

| 维度 | Tools | Agent | Workflow |
| --- | --- | --- | --- |
| 决策能力 | 无（只执行，不决策） | 有（LLM 自主动态决策） | 无（开发者在代码里写死） |
| 执行方式 | 被动，等待被调用 | 主动，自主循环直到完成 | 按开发者定义的顺序执行 |
| 确定性 | 高（输入固定则输出固定） | 低（同输入可能走不同路径） | 高（行为完全可预测） |
| 灵活性 | 只做一件事 | 高（能应对预料之外的情况） | 低（流程提前写死，难以动态调整） |
| 调试难度 | 容易（单一函数） | 难（执行路径不确定） | 容易（链路清晰，可逐步追踪） |
| 适用场景 | 封装单一具体能力 | 路径未知的复杂任务 | 流程相对固定的业务系统 |

实际工程里最主流的模式是 **Agentic Workflow**：用 Workflow 固定主流程的骨架，在需要灵活判断的节点嵌入 Agent，其余固定节点直接用 LLM 或 Tools。骨架是确定的，让你能控制整体行为、便于调试；关键节点是灵活的，让你能应对各种复杂情况。

### Agent 设计范式

#### ReAct（Reasoning + Acting）

ReAct 是最常见的 Agent 设计范式，核心机制是把推理（Reasoning）和行动（Acting）交替进行。每一轮循环由三个步骤组成：

- **Thought（思考）**：LLM 分析当前情况，决定下一步该做什么
- **Action（行动）**：根据思考的结论调用工具
- **Observation（观察）**：工具返回的结果反馈给 LLM，进入下一轮思考

ReAct 的优势是实现简单、灵活度高、逻辑透明；短板是长流程任务容易跑偏，没有全局规划约束方向。

#### Plan-and-Execute（规划-执行）

Plan-and-Execute 是针对 ReAct「长任务容易跑偏」的优化方案。核心区别是：

- **ReAct**：走一步看一步，边想边干，规划和执行混在一起
- **Plan-and-Execute**：先把完整计划定好，再按计划一步步干，规划和执行完全解耦

整个流程分三个阶段：
1. **规划阶段**：Planner 把用户任务拆成步骤清单
2. **执行阶段**：Executor 按清单逐步执行
3. **重规划阶段**：每执行完一步，检查是否需要调整后续计划

Plan-and-Execute 的优势是整体结构清晰，复杂任务不容易跑偏，还支持「强模型规划、弱模型执行」的成本优化策略。代价是灵活度不如 ReAct，实现更复杂。

#### Reflection（反思）

Reflection 不是独立的完整流程，而是给 ReAct 或 Plan-and-Execute 加的「质量增强 buff」。核心循环是「生成 -> 评估 -> 改进」：

1. **生成**：Agent 完成输出
2. **评估**：独立的评估模块（可以是 LLM 自身或专门的 Critic Agent）检查输出质量
3. **改进**：根据评估意见修改输出，直到达标或达到最大轮次

评估 prompt 的关键设计：
- 给出明确的检查维度（事实、逻辑、完整性、表达）
- 必须有「PASS」机制，给 LLM 一个「够好了就停」的出口

Reflection 的优势是输出质量明显提升，适合代码生成、文案写作等质量要求高的场景。代价是至少多一次 LLM 调用，token 消耗和延迟都会增加。

**Reflexion** 是 Reflection 的进阶版本，不仅检查输出，还会把失败原因总结成「经验教训」存入记忆，下次遇到类似任务时参考，避免重蹈覆辙。

### Agent 推理模式

#### CoT（Chain of Thought，思维链）

CoT 是最基础的推理模式，核心是在 prompt 里加一句「让我们一步步思考」，让 LLM 先把推理步骤写出来，再给答案。

为什么有效？因为 LLM 的输出是顺序生成的，先写出来的推理内容会进入上下文，成为后续生成的依据，帮助 LLM 不跳步、不乱想。

CoT 有两种触发方式：
- **Zero-shot CoT**：直接加提示语，零成本但效果不稳定
- **Few-shot CoT**：给几个带推理过程的例子，效果更稳定但需要准备示例

CoT 的局限是只有一条推理路径，一旦走错方向，整条链就歪了，没有任何纠偏机制。

#### ToT（Tree of Thoughts，思维树）

ToT 针对 CoT「一旦走错就全错」的问题，核心改变是同时探索多条推理路径：

1. **生成多个候选思路**：让 LLM 针对同一问题给出多个不同方向
2. **评估每个思路的可行性**：给每个思路打分
3. **选优继续深入、剪掉差的**：只保留高分思路，展开下一层推理

ToT 的代价是多次 LLM 调用，典型设置下成本是 CoT 的 3-5 倍。

#### GoT（Graph of Thoughts，思维图）

GoT 在 ToT 基础上更进一步，把推理结构从树换成图，允许不同路径的中间结果合并、复用。一个推理节点可以接收来自多个前置节点的输出作为输入。

GoT 能建模的推理模式比 ToT 更丰富，但落地复杂度很高，目前主要还是学术研究场景。

### Agent 记忆系统

Agent 的记忆机制分四层，从最短暂到最持久：

| 类型 | 载体 | 容量 | 生命周期 | 访问方式 |
| --- | --- | --- | --- | --- |
| 感知记忆 | 当次输入 | 极小 | 单次调用 | 即时访问 |
| 短期记忆 | context window | 受 token 限制 | 一次任务 | 直接读取 |
| 长期记忆 | 向量/关系数据库 | 无限 | 持久 | 语义检索 |
| 实体记忆 | 结构化存储 | 无限 | 持久 | 精确查询 |

**感知记忆**：当前调用的原始输入，生命周期只有一次调用。

**短期记忆**：context window 里的 messages 列表，维持当前任务执行过程中的完整状态。任务结束就清空。

**长期记忆**：跨任务保留的信息，存在外部数据库里。核心技术是向量数据库 + Embedding，支持语义检索。

长期记忆还可细分为三种子类型：
- **情节记忆**：具体事件经历（如「上周用户让我写爬虫，遇到反爬问题」）
- **语义记忆**：通用知识和规律（如「动态渲染网站要用 Selenium」）
- **程序记忆**：操作流程和方法论（如「部署 Flask 的标准步骤」）

**实体记忆**：从对话中提炼出来的结构化事实，比如「用户偏好 Python」「预算上限 5 万」。信息密度最高，查询快。

### 记忆压缩方法

当 context window 快满时，常用的记忆压缩方法：

**滑动窗口**：只保留最近 N 轮对话，更早的直接丢弃。实现简单但会丢失早期重要信息。

**摘要压缩**：用 LLM 把即将超出窗口的历史总结成摘要，用摘要替换原始对话。会丢失细节，但保留了关键脉络。

**层级式摘要**：分层处理，最近 10 轮保持原文，10-50 轮压缩成中期摘要，50 轮之前压缩成长期摘要。

**重要性过滤**：给每条对话记录打重要性分数，低于阈值的淘汰，高分的保留。

**结构化抽取**：把关键信息提取成结构化字段存储，信息密度最高。

### Multi-Agent（多智能体）

Multi-Agent 是多个 Agent 协作完成任务，每个 Agent 各有分工。使用 Multi-Agent 的主要驱动因素：

1. **Context 窗口限制**：单个 Agent 处理复杂任务时信息量一旦超出窗口就开始「遗忘」
2. **专业度问题**：让一个 Agent 身兼数职，每件事都做得不够专注
3. **并行执行**：多个 Worker 同时跑，整体效率提升

#### Multi-Agent 协作模式

**顺序流水线（Sequential Pipeline）**：Agent A 做完把结果交给 Agent B，B 做完交给 Agent C，像工厂流水线一样依次处理。

**并行扇出（Fan-out）**：一个调度者把多个独立子任务同时分发给不同的 Worker Agent，它们各自并行执行，最后由调度者收集汇总。

**辩论/评审模式（Debate/Review）**：多个 Agent 对同一个问题各自给出方案，然后由一个裁判 Agent 或它们互相评审来筛选最优解。

#### Multi-Agent 架构方案

**中心化方案（Orchestrator 模式）**：
- 一个 Orchestrator（总调度员/项目经理）负责：读懂用户目标、拆成子任务、判断每个子任务交给哪个 Worker、收集 Worker 产出拼成最终答案
- Worker Agent 只关注自己的职责，context 干净，只装和自己相关的信息
- 工程上几乎都用这个方案，因为可控、可追踪、出问题能排查

Orchestrator 有几种变体：
- **静态路由**：任务拆分和分配规则预先定义好
- **动态规划**：Orchestrator 本身是一个 LLM，根据用户输入动态生成任务计划
- **自适应编排**：不仅动态规划，还会根据 Worker 执行结果实时调整后续计划

**去中心化方案（Peer-to-Peer）**：
- 没有总调度，多个 Agent 通过共享消息队列或状态空间自行协商、直接通信
- 听起来灵活，但工程上很少用，因为：任务分配没有协调、执行顺序没有保证、失败没有感知、没有人确认任务整体完成

#### 选型决策

| 维度 | Single-Agent | Multi-Agent（中心化） | Multi-Agent（去中心化） |
| --- | --- | --- | --- |
| 架构复杂度 | 低 | 中 | 高 |
| Context 压力 | 全部压在一个 Agent | 各 Agent 独立管理 | 各 Agent 独立管理 |
| 专业能力 | 泛才 | 专才分工 | 专才分工 |
| 并行能力 | 不支持 | 支持子任务并行 | 支持并行 |
| 可控性 | 高 | 高 | 低 |
| 调试难度 | 容易 | 中 | 难 |
| 工程实用性 | 高 | 高 | 低 |
| 适用场景 | 任务清晰、复杂度适中 | 需要分工或并行的复杂任务 | 学术探索场景 |

**渐进式演进策略**：先用 Single-Agent 把系统跑起来，当发现某个环节成为瓶颈（context 经常撑满、某类子任务质量不行），再把那个环节拆出来交给专门的 Worker Agent。

### Agent 评估

评估 Agent 效果可以从三个层面：

**任务完成度**：Agent 是否完成了用户指定的目标，输出是否符合预期。

**工具调用准确性**：调用的工具是否正确，参数是否准确，是否避免了不必要的工具调用。

**效率指标**：
- 平均步数：完成任务需要的平均循环轮数
- Token 消耗：每次任务的总 token 使用量
- 延迟：端到端响应时间

**质量指标**：
- 幻觉率：输出中包含事实错误的比例
- 用户满意度：人工评估或用户反馈

### Agent 落地难点

**第一难：行为不确定性**。Agent 的执行路径是 LLM 实时决定的，同样的输入可能走不同的路径，测试覆盖率天然就低，出了问题难以复现。

**第二难：调试困难**。执行链路长，涉及多轮 LLM 调用和工具调用，中间任何一步出问题都可能导致最终结果错误，排查起来很困难。

**第三难：成本失控**。Agent 可能陷入无限循环，或者调用过多工具，导致 token 消耗和延迟远超预期。必须有最大步数、token 预算、超时等停止条件。

**第四难：工具设计**。工具的描述要精确，参数设计要简洁，错误信息要清晰，否则 LLM 无法正确理解和使用工具。

### 框架 vs 手搓

**框架（如 LangChain、LangGraph）的优势**：
- POC 阶段快速验证 idea
- 省掉大量样板代码
- 内置 tracing、callback、记忆管理

**框架的痛点**：
- 抽象层太多，调试时不知道哪步出问题
- 版本升级经常有 breaking change
- 通用设计产生隐性性能开销

**手搓的优势**：
- 链路透明，可观测性好
- 精确裁剪，没有多余开销
- 稳定可控，不受框架升级影响

**实践建议**：核心逻辑手写（工具调用循环、对话历史管理、错误处理），周边工具性功能借用框架（tracing、文档解析、向量库客户端）。

Anthropic 的官方建议：不要一上来就用框架，先用最少的抽象把核心逻辑跑通。框架帮你快速搭起来的东西，往往也是后期最难排查的东西。

### Agent 工具调用架构

Agent 的工具调用涉及三个层次的协议，从底到顶依次是 [[ToolCalling|Function Calling]]、[[MCP]]、[[AgentSkill]]：

- **Function Calling**：最底层的调用协议，定义模型怎么表达「我要调哪个函数、参数是什么」
- **MCP**：在 Function Calling 之上做工具标准化，定义工具怎么暴露给模型，一次实现到处复用
- **Agent Skill**：在最上层做知识和流程封装，定义拿到工具后按什么流程完成任务

完整的链条是：Skill（定义流程）-> MCP（提供工具）-> Function Calling（模型触发调用）。

多个 Agent 之间协作时，可以通过 [[A2A]] 协议进行通信和任务委派。
